Rerank 重排与上下文压缩：召回准确率 78%→92% 的关键两步
字数总计：891   |   阅读估时：3分钟

  2. 上下文压缩：第二个被忽视的环节

上篇讲了双路召回把候选捞回来，但”捞得全”不等于”喂得准”。这篇讲 RAG 链路的最后两个提质环节：重排精筛和上下文压缩——正是这两步把我们端到端召回准确率从 78% 拉到了 92%（内部 200 题标注集）。

为什么必须重排

召回阶段的打分器（向量相似度 / BM25）是粗排：为了全库检索的速度，模型轻、特征少，它对”候选里谁和问题最相关”的判断是模糊的。

重排用的是交叉编码器（Cross-Encoder）：把 query 和每篇候选文档拼在一起送进模型，做深度注意力交互。直观理解——粗排像”看简历筛人”（各自独立打分），重排像”面试对谈”（对照着问），判断精度完全不是一个量级，代价是速度慢、只能处理几十个候选——所以它天然适合放在召回之后。

实践参数：候选 1520 个进重排，出 58 个进 Prompt。top_n 别贪大——注入的资料越多，模型注意力越稀释，”给模型更多资料效果更好”是 RAG 最常见的错觉。

上下文压缩：第二个被忽视的环节

重排后的文档往往一篇几百字，其中大半是和问题无关的铺垫（章节背景、前后文过渡）。全量注入的问题：

  1. Token 成本：长上下文按 token 计费，企业客户每天几万次问答，浪费很实在；
  2. lost in the middle：模型对超长上下文中段的信息利用率显著下降，资料塞太多反而答不准。

压缩的两种做法：

文档级压缩（简单有效，先上这个）：重排时就以”段落”为检索单元而非整篇文档，捞出来的天然就是相关片段；

句级压缩（LLM 压缩器）：对 top 文档再过一个小模型，只保留与问题相关的句子：

注意压缩必须保留原文措辞（摘句不改写），改写会引入模型的二次幻觉——引用溯源就没法做了。

答案引用与低置信兜底

92% 的准确率意味着还有 8% 的失败。工程上的态度不是追求 100%，而是让失败可控可解释：

  • 每个注入片段带来源编号，生成时强制模型标注 [1][2] 引用，前端可点击查看原文；
  • 设置置信阈值：重排最高分低于阈值、或检索片段与问题相关度整体偏低时，不硬答，返回”资料库暂未覆盖该问题”并引导提工单——显式兜底好过一本正经的臆造，这是 to B 客户最认的体验。

小结

RAG 的完整链路至此闭环：查询改写 → 双路召回（向量+BM25）→ RRF 融合 → Rerank 精排 → 上下文压缩 → 带引用生成 → 置信兜底。78%→92% 没有任何单点魔法，全靠每个环节各抠几个点。工程的魅力恰恰在于：把不确定的模型，装进确定的管道。
