LangGraph 入门：用 StateGraph 编排多 Agent DAG 工作流
字数总计：745   |   阅读估时：2分钟
  1. 为什么需要编排框架
  2. StateGraph 实战骨架
  3. 断点与可观测性

单个 Agent 像一个什么都能干但什么都干不精的全栈；多 Agent 系统则像一支分工明确的团队。这篇以我做 API 开放平台智能客服系统的经验，讲讲 LangGraph 怎么把多个 Agent 编排成一张可控的 DAG。

为什么需要编排框架

裸写多 Agent 循环的代码长这样：意图识别完调文档 Agent，文档答不了转 API 诊断 Agent，还要记状态、传结果、异常兜底……几十个 if-else 堆起来，状态散落在函数参数里，改一个流程牵动全身。

LangGraph 的核心抽象只有两个：State（全局状态） 和 Node（节点）。每个节点是一个”干活的 Agent”，读共享 State、写共享 State；节点间的转移关系构成有向图。编排逻辑从”调用链代码”变成了”图定义”。

StateGraph 实战骨架

几个设计要点，都是被线上问题教育出来的：

1. 固定 DAG，不做自由协作。 LangGraph 支持 Agent 之间互相 @（AIA 全自主多智能体），我们最终收敛成固定路由 + 并行扇出的 DAG：router 定向分发，专业 Agent 并行执行，reviewer 统一收口。自由协作的对话式 Agent 之间会互相客气、绕圈不收敛，客服场景要的是确定性和低延迟。

2. State 是唯一真相。 所有 Agent 通过 State 交换数据，不允许直接互调——这样每个节点可以单独测试、单独替换模型，trace 也天然按 State 变更记录。

3. 审查节点放末端。 所有产出必须经过统一的安全审查节点再输出（后面脱敏那篇单独讲为什么位置这么重要）。

断点与可观测性

LangGraph 自带 checkpoint 机制，State 每次变更可持久化。带来两个直接收益：

  • 会话记忆：用户第二轮追问时从 checkpoint 恢复上下文，不用全量重放；
  • 逐节点 trace：每个节点的输入输出耗时都有记录，前端能展示”这个问题经过了哪些 Agent、各自耗时多少”——评测可解释就建立在这之上。

小结

LangGraph 给多 Agent 系统的贡献是把”AI 的灵活性”和”工程的确定性”缝在了一起：节点内是概率性的模型决策，节点间是确定性的图流转。下一篇讲 MCP——这些 Agent 干活时调用的工具生态怎么标准化。
