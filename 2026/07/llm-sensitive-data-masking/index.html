大模型应用的敏感信息治理：三层脱敏体系设计
字数总计：908   |   阅读估时：3分钟

大模型应用的数据安全有个残酷的现实：你的日志、Prompt、模型供应商，都可能成为敏感数据的泄漏面。这篇讲我们在多 Agent 系统里落地的三层脱敏体系，以及一个血泪教训：安全节点的位置必须在架构上保证，不能靠自觉。

敏感信息清单先行

脱敏之前先盘清楚”什么算敏感”。我们定义了八类：

手机号、身份证号、邮箱、API Key/Token、银行卡号、IP 地址、姓名+工号组合、自定义密钥串。每一类配一条正则/规则，统一注册在脱敏规则引擎里，新规则上线走安全评审——脱敏规则本身也是安全资产。

三层防线

第一层：用户输入脱敏（入口）

用户问题进系统的第一站。手机号、身份证这类强模式信息直接打码：

打码后的文本进 Prompt，但原始文本保留在会话上下文里用于业务逻辑（比如工单里要留真实手机号）——脱敏是防模型和日志，不是防业务本身。

第二层：工具日志脱敏（过程）

多 Agent 系统里每个节点的输入输出都记 trace，这是调试命根子，也是泄漏重灾区：Agent 调工具时，工具返回里可能带着用户手机号、内部 token。trace 落盘前统一过脱敏管道——trace 系统默认敏感，接入时就要过安全评审。

第三层：最终输出脱敏（出口）

模型的最终回答也可能复述敏感信息（”您的手机号 138xxxx 已重置”——用户自己输入的，但输出到公共渠道就是泄漏）。出口再过一遍规则引擎 + 一个专门的敏感分类小模型（规则能兜住 95%，模型兜长尾）。

血泪教训：安全节点的位置决定成败

我们最初把”安全审查”作为可选节点挂在编排图的分支末端——文档 Agent 链路挂了，账单 Agent 忘了挂。联调时账单链路的 trace 里赫然出现明文手机号。

修复方案不是”补上遗漏的节点”，而是把审查收敛为编排图的强制单出口：

reviewer 在 DAG 里是 END 之前的必经节点，结构上保证没有绕过的路径。这比”开发规范要求大家都加审查”可靠一百倍——安全要靠架构保证，不能靠约定保证。上 LangGraph 那篇说 reviewer 放末端，来历就是这里。

几个容易漏的点

  • 错误信息：异常栈里的 SQL、内部 URL 同样要脱敏后出网；
  • 缓存：脱敏后的数据才允许进共享缓存；
  • 人在环：教师改分、人工客服接管时，操作界面上敏感字段默认打码，点”查看完整信息”的动作本身记审计日志。

小结

三层脱敏的本质是把安全从”某个环节的功能”变成”系统的不变式”：入口净化、过程留痕脱敏、出口强制审查。to B 场景里，这套体系是过安全评审、拿私有化订单的门票——安全不是成本，是签单能力。
