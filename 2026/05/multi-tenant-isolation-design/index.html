企业级多租户设计：租户/组织/角色三层隔离的落地路径
字数总计：858   |   阅读估时：3分钟

to B 产品和 to C 产品架构上最大的分水岭就是多租户。一个客户的数据漏到另一个客户面前，不是 bug 是事故。这篇复盘企业版智能体平台的三层隔离体系：租户 → 组织 → 角色，每一层怎么落地。

模型设计：三层结构

核心原则一句话：数据归属看租户，数据范围看组织，操作能力看角色。一个用户查询知识库时，租户决定”能查哪批库”，组织决定”库里哪些目录可见”，角色决定”能做检索还是能管理”。

隔离落点：四层防线

只在应用层 where tenant_id = ? 是不够的——一个遗漏就是穿透。我们把隔离下沉到四个层：

1. 数据层：所有业务表带 tenant_id 字段，MyBatis 拦截器自动注入过滤条件（不是靠人肉写 where）：

拦截器里 require() 取不到租户上下文就抛异常拒绝查询——“默认放行”是隔离代码里最危险的写法。

2. 缓存层：Redis key 统一前缀 t:{tenantId}:biz:key。key 设计评审时逐个核对，漏一个前缀就是跨租户读缓存。

3. 知识库层：向量库（Milvus）按租户建 Collection 或 partition，索引物理隔离；ElasticSearch 用 index alias + 租户后缀。AI 应用的多租户容易只顾 SQL 忘了向量库——模型检索的每一跳都要过租户边界。

4. 文件层：对象存储路径 /{tenantId}/...，下载走临时签名 URL，服务端校验路径前缀与当前租户一致。

跨组织访问：显式而非静默

集团客户有跨部门协作需求，一刀切禁止不现实。方案是显式授权 + 上下文提醒：

  • 组织 A 的成员要访问组织 B 的资源，需 B 管理员显式授权，授权记录带过期时间；
  • 访问时前端常驻横幅”您正在查看 XX 部门的资源”——让越界访问在 UI 层可见；
  • 所有跨组织读写进审计日志（谁、何时、访问了什么）。

角色与权限：RBAC 够用，别过度设计

perm.has 内部先查角色权限点，再校验该知识库对用户是否可见（租户+组织范围）。to B 场景 90% 的需求 RBAC 都能覆盖，ABAC 那套属性级策略引擎留到真有需求再上——权限模型每复杂一分，交付和排障成本就涨十分。

小结

多租户隔离是典型的”防御纵深”工程：不信任任何单层防护。应用层过滤、拦截器兜底、物理层分区、审计层追溯，四层互为备份。上线前的必修课是渗透测试：用租户 A 的会话 token 拼各种接口调租户 B 的资源 ID，能穿透任何一层都算失败。
