MCP 协议详解：从设计原理到手写一个 MCP Server
字数总计：898   |   阅读估时：3分钟

做企业智能体平台时，MCP（Model Context Protocol）是工具生态的地基。这篇讲清楚三件事：MCP 解决什么问题、协议长什么样、自己写一个 Server 要几步。

MCP 之前的世界：N×M 集成地狱

在 MCP 出现前，每个 AI 应用对接每个工具都要写专属适配代码：n 个模型应用 × m 个工具系统 = n×m 套集成。而且各家 Function Calling 的函数描述格式、鉴权方式、调用协议都不统一。

MCP 的思路和当年的 JDBC 如出一辙：定一个统一协议，工具方实现一次 Server，任何支持 MCP 的 Agent（Host/Client）都能即插即用。M=1，复杂度从 n×m 降到 n+m。

协议三角色

Server 向 Client 暴露三类能力：

  • Tools：可调用的函数（最常用，对应 Function Calling）；
  • Resources：可读取的数据源（文件、数据库表）；
  • Prompts：可复用的提示词模板。

传输层支持 stdio（本地进程）和 Streamable HTTP（远程服务）。企业场景基本都是 HTTP：Server 部署在内网，带鉴权，多租户隔离。

企业级落地的四个关键

协议跑通只是 10%，生产化才是大头：

1. 注册与发现。 平台侧要有 MCP Server 注册中心：Server 元信息（能力清单、版本、负责人）、健康检查、按租户/角色的可见性配置。企业里工具只会越来越多，”哪些智能体允许挂哪些工具”必须是配置化的。

2. 鉴权。 Streamable HTTP Server 挂在内网也要鉴权：平台调用 Server 时带上服务身份 Token（不是终端用户的），Server 侧按调用方收敛工具清单——防止一个智能体越权调用财务系统的接口。

3. 参数校验与超时。 Server 是不可信边界的延伸：模型可能传非法参数，必须 schema 校验后落库/调接口；工具超时设上限（比如 10s），超时降级为错误信息回传模型，别让一个慢工具拖死整条编排链路。

4. 审计留痕。 每次 tools/call 记录：哪个智能体、哪个用户会话、调了什么工具、参数摘要、结果摘要、耗时。出了问题能回放，这是企业客户验收的硬指标。

小结

MCP 之于 Agent 生态，如同 JDBC 之于数据库生态、USB-C 之于外设：协议统一后，工具生态才能规模化。从 Function Calling 到 MCP，变化的不是”模型能调工具”这个能力本身，而是**工具从”每个应用私有”变成”全生态共享的资产”**。
