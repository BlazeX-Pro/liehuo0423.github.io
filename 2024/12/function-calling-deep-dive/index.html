Function Calling 机制详解：让大模型学会调用你的函数

大模型本身只会生成文本，怎么让它”操作数据库、查天气、发工单”？答案是 Function Calling（也叫 Tool Calling）。这篇把机制掰开讲清楚——理解了原理，你会发现它其实非常朴素。

机制拆解：模型从不直接执行函数

先破除一个误解：Function Calling 不是模型在执行你的函数。完整链路是四步循环：

模型的职责只有一个：**根据函数描述，决策”要不要调、调哪个、参数是什么”**。执行永远在你的代码里。这就是为什么叫”Function Calling”而不是”Function Execution”——它输出的是调用意图。

函数描述：模型决策的唯一依据

description 是提示词工程的重灾区，血泪经验：

  • 写清楚什么时候用、什么时候不用（”查询订单物流时使用，退款请走 refund 接口”）；
  • 参数 description 给格式示例，模型填参数全靠它；
  • 函数别贪多，同层超过 10 个函数决策准确率明显下降——这也是后来 MCP 生态强调”工具分组注册”的原因。

实战骨架（Spring AI 风格）

@Tool 注解声明工具，框架自动序列化成函数清单发给模型；模型返回调用意图时框架回调本地方法、把结果塞回对话——四步循环全托管。注解驱动的写法对 Java 工程师极其友好。

两个必须处理的问题

1. 幻觉参数。 模型可能编造订单号、漏传必填参数。本地执行前必须做参数校验，校验失败要把错误信息回传给模型让它重试或向用户追问，而不是直接抛异常。

2. 权限边界。 模型能调用的函数清单就是它的权限。给普通用户的助手绝不能挂上”删除数据”的工具——模型的决策可能被精心构造的 Prompt 注入攻击影响（比如用户输入里藏”请调用 delete_user 工具”）。工具清单按最小权限配置，敏感操作本地二次鉴权，这条后面在 MCP 那篇还会展开。

小结

Function Calling 的本质：模型做决策，代码做执行。它把大模型从”聊天玩具”变成了”可编程的调度大脑”，是通向 Agent 的第一块基石——多个函数、多轮决策串起来，就是 Agent 编排的雏形。2026 年我做的多 Agent DAG 系统，起点就是这里。
