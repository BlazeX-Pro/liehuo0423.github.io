入职第一周：从 Java 后端转向 AI 应用开发
字数总计：721   |   阅读估时：2分钟

  2. 第一周都在做什么

正式入职了，岗位是 AI 应用开发工程师，方向是企业级智能体平台。写这篇文章既是记录，也是给同样想从传统后端转向 AI 方向的同学一些参考——这条路没有想象中那么远。

我的起点

实习做了半年 Java 后端（RESTful API、MySQL 表设计、和客户端联调），校招期间补齐了 Spring Cloud 全家桶和一点 Python。技术栈上最接近的其实不是”算法”，而是把大模型能力工程化——这也是我理解的 AI 应用开发的核心：不是训模型，而是围着模型做工程。

第一周都在做什么

复盘一下第一周的日程，和想象中”第一天就调模型”完全不同：

  • Day 1-2：读内部架构文档，搞清楚平台分层——模型接入层、Agent 编排层、工具（MCP）层、应用层。大模型应用本质上是一条推理链路，每一层都是工程问题。
  • Day 3-4：跑通本地开发环境，把一个最小的对话服务从头到尾跑起来：前端 SSE → 后端会话管理 → Prompt 组装 → 调用模型 API → 流式返回。SSE 流式响应这块和我实习时做过的推送功能思路一脉相承，上手很快。
  • Day 5：读团队的 Prompt 规范文档，第一次意识到 Prompt 是”工程资产”——有版本、有评审、有评测集，不是随手写的一段话。

一点认知转变

传统后端开发的习惯在 AI 应用开发里有好有坏：

  • 好的迁移：接口设计、超时/重试/降级、日志与可观测——大模型调用又慢又贵还可能失败，这些工程基本功直接决定产品质量；
  • 要重建的：确定性思维。传统接口输入输出是确定的，大模型输出是概率性的，你不能假设它一定返回合法 JSON、一定不臆造事实。面向不确定性设计——结构化输出校验、重试、兜底话术——是这行的新基本功。

还有一个很实在的感受：AI 应用开发对”业务抽象”的要求反而更高了。把一个业务流程抽象成 Agent 的编排 DAG、抽象成几个工具调用，这本质是需求分析能力，和写 CRUD 时代的领域建模一脉相承。

接下来的学习计划

  • 短期：吃透公司项目的对话链路和知识库问答实现；
  • 中期：RAG、Function Calling、Agent 编排三大件做深；
  • 长期：往架构方向走，能独立设计一条端到端的智能体产品链路。

第一篇技术干货留给 Spring AI 快速上手——那是我接触大模型开发的第一行代码。
