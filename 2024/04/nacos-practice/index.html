Nacos 注册中心与配置中心入门实战
字数总计：649   |   阅读估时：2分钟

准备校招那阵子把 Spring Cloud Alibaba 的核心组件过了一遍，Nacos 是其中最常用的一个：既是注册中心（服务发现），又是配置中心（动态配置）。这篇是我搭 demo 时的理解笔记。

为什么需要注册中心

没有注册中心时，服务 A 调服务 B 要在配置文件里写死 B 的地址。B 扩容成 3 个实例、或者换了 IP，A 就得改配置重启——服务一多这就是灾难。

Nacos 的解法：服务启动时把自己的 IP:端口注册上去，调用方按服务名从 Nacos 拉取实例列表，本地负载均衡后调用。实例上下线自动感知，调用方无感。

配置中心：动态改配置不用重启

在 Nacos 控制台把 sync.max-retry 从 3 改成 5，接口立刻返回 5，全程不用重启。线上调开关、改限流阈值、切降级文案，都靠这个。

命名规范建议 应用名-环境.yaml（如 file-service-dev.yaml），配置分组用命名空间隔离环境，开发/测试/生产互不干扰。

两个必踩的坑

坑一：临时实例 vs 持久实例。 默认注册的是临时实例，靠客户端心跳维持（默认 15 秒一次），Nacos 30 秒收不到心跳标记不健康、15 秒后剔除。如果你的服务启动慢、心跳还没发出来就被摘了，检查 instance-enabled 和健康检查间隔配置。

坑二：服务名大小写。 Nacos 服务名默认大小写敏感，File-Service 和 file-service 是两个服务，Feign 调用直接 No instance available。团队里统一小写中划线，能省掉一堆排查时间。

小结

Nacos 一句话总结：**注册中心解决”服务在哪”，配置中心解决”配置怎么变”**。它是 Spring Cloud Alibaba 体系的基石，后面 Sentinel 的规则下发、Gateway 的动态路由都依赖它。下一篇写 Sentinel 怎么在这个基础上加限流熔断。
