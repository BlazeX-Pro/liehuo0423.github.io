Sentinel 上手：给 Spring Boot 接口加限流熔断
字数总计：654   |   阅读估时：2分钟

一个没有限流保护的接口，本质上是在赌流量永远不会超过你的承受能力。这篇记录 Sentinel 在 Spring Boot 项目里的接入过程，重点是 QPS 限流和慢调用熔断这两个最常用的规则。

接入：三步走

启动 Sentinel Dashboard（一个独立的 jar），流量经过接口后就能在控制台看到实时监控，规则也在控制台动态下发——规则变更不需要重启，这是它比 Hystrix 好用的核心原因。

规则一：QPS 限流

最简单的流控规则：资源 GET:/file/sync，阈值类型 QPS，单机阈值 100。超过 100 的请求直接抛 BlockException。

规则二：慢调用熔断

对查询类接口，我更喜欢慢调用比例熔断：RT 超过 500ms 的请求占比超过 50%，熔断 10 秒，期间直接走降级方法返回缓存数据或默认值。这比 QPS 限流更贴合真实故障——下游变慢时主动断开，防止线程池被打满拖垮整个服务。

注意 fallback 只管业务异常，限流/熔断抛的 BlockException 要用 blockHandler 指定，两者职责分开，排查问题时一眼能分清是”被限了”还是”业务挂了”。

规则持久化

控制台配的规则默认只存在内存，Dashboard 一重启规则全丢。生产环境要接 rules 持久化到 Nacos 数据源，配置中心存 JSON 规则，应用启动时加载、变更时监听推送。这一步是 demo 和生产的分水岭。

小结

限流熔断的本质是用可控的失败替代不可控的雪崩。Sentinel 的接入成本很低，真正值钱的是规则的经验积累：核心接口限多少 QPS、降级返回什么内容、熔断恢复后要不要半开试探——这些才是架构设计里”稳定度”的具体形状。
