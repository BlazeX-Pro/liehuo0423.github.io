MySQL 慢查询优化手记：一次文件同步接口的排查

实习期间接手过一个文件同步状态查询接口，P99 能飙到 1.2 秒，用户在客户端点”同步记录”要转圈好几秒。这篇复盘一下当时的排查和优化过程，套路基本上是通用的。

EXPLAIN 一看：type: ALL，全表扫描，rows: 187万。原因一目了然——表上只有主键索引，user_id 裸奔。

第二步：加对索引

直觉是给 user_id 加索引，但注意 WHERE 里还有 sync_status，ORDER BY 用的是 updated_at。联合索引的列序很讲究：

为什么是这个顺序？等值查询的列在前，范围/排序列在后：user_id = 是等值，sync_status IN 本质也是多个等值，updated_at 用于排序。这样索引既能完成过滤，又能直接产出有序结果，避免 filesort。

加完再 EXPLAIN：type: range，Extra 里 filesort 消失了，查询从 800ms 降到 8ms。

第三步：那些容易忽略的坑

坑 1：隐式类型转换。 如果表里 user_id 是 bigint，查询时传了字符串 '10086'，索引直接失效（WHERE user_id = '10086' 会触发 CAST 函数作用在列上）。这个坑我在联调时踩过一次，接口突然变慢全表扫描，查了半天是客户端 SDK 把 id 序列化成了字符串。

坑 2：IN 列表过长。 sync_status IN (...) 传几十个值时优化器可能放弃索引改走全表。业务上尽量控制枚举值数量。

坑 3：分页深翻页。 LIMIT 100000, 20 这种写法要先扫描 10 万行再丢弃。改成游标式分页：

小结

排查口诀：慢查询日志定位 → EXPLAIN 看执行计划 → 对症下药（索引/SQL/数据量）→ 压测验证。加索引前一定要想清楚列序和基数，别无脑 user_id, updated_at 一把梭——区分度低的列放前面，索引效果会大打折扣。
